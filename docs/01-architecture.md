# 01 · 架构

## 1. 分层

```
┌──────────────────────────────────────────────────────────────────────┐
│ experiments/    一次研究一个目录：图 + 参数 + 记录 + 产出              │
├──────────────────────────────────────────────────────────────────────┤
│ research/       我们的代码：pass 插件库、共享 C++ 头                   │
├──────────────────────────────────────────────────────────────────────┤
│ tools/          构建/运行/抓帧/度量/脚手架（PowerShell 7 与 5.1 均可）  │
├──────────────────────────────────────────────────────────────────────┤
│ vendor/falcor/  Falcor 9.0，只读子模块：框架、上游 pass、Mogwai        │
└──────────────────────────────────────────────────────────────────────┘
```

三条边界是硬的：

1. **不 fork 上游**。研究代码永远在 `research/`，Falcor 永远是 `git submodule` 指针。
2. **不手改生成物**。`vendor/falcor/Source/RenderPasses/CMakeLists.txt` 里的
   `eidolon overlay` 块由 `tools/sync-passes.ps1` 生成。
3. **产物不入库**。`out/`、`experiments/*/results/`、`assets/` 全部 gitignore。

## 2. 注入机制（本仓库最需要理解的一处）

Falcor 是整个构建的**顶层 CMake 工程**——它内部大量使用 `${CMAKE_SOURCE_DIR}`
（data/scripts 复制、deploy 脚本、packman 路径），所以**不能**把 Falcor 当子目录
`add_subdirectory()` 塞进我们的工程。反过来，Falcor 发现插件库的唯一方式是
`Source/RenderPasses/CMakeLists.txt` 里的一行 `add_subdirectory()`。

于是我们注入，而不是修改：

```powershell
pwsh -File tools\sync-passes.ps1
```

它做的事，逐字可预测：

1. `git -C vendor/falcor show HEAD:Source/RenderPasses/CMakeLists.txt`
   → 拿到**纯净的上游内容**（不依赖工作区状态）；
2. 追加一段带标记的生成块（幂等，重复跑字节一致）：

```cmake
# >>> eidolon overlay (generated by tools/sync-passes.ps1; do not edit)
add_subdirectory(D:/Eidolon/research/shared ${CMAKE_BINARY_DIR}/eidolon/shared)
add_subdirectory(D:/Eidolon/research/passes/HelloPass ${CMAKE_BINARY_DIR}/eidolon/HelloPass)
# <<< eidolon overlay
```

`research/apps.txt`（可选，默认为空）里登记的应用会以同样方式追加到同一个块里，
走 `add_falcor_executable()` 而非 `add_plugin()`——两者构建语义不同，清单也故意分开。

3. 以 UTF-8（无 BOM）写回。

要点：

- **源目录是绝对路径**，指向仓库树外，所以必须显式给第二个参数（构建目录）。
  CMake 允许绝对源目录，这也是不用 junction/symlink 的原因。
- **绝对路径意味着仓库不能随意搬家**。搬完重跑 `sync-passes.ps1`（`verify.ps1` 会比对）。
- 生成文件以 **LF** 写入。Falcor 的 `.gitattributes` 是 `* text=auto`，所以在
  `core.autocrlf=true` 的 Windows 上，工作区里的其他文件可能是 CRLF，而这一个文件是 LF。
  `git -C vendor/falcor diff` 仍然只显示我们的新增行（git 比对前会归一化）——真实上游 9.0
  文件上实测：**5 行新增、0 行删除**。
- `research/shared` 必须排在所有 pass 之前：pass 都 `target_link_libraries(... EidolonShared)`。
- 撤销：`tools\clean-passes.ps1`（等价于 `git -C vendor/falcor checkout -- Source/RenderPasses/CMakeLists.txt`）。

## 3. 插件契约（Falcor 侧，已核实）

| 环节 | 事实 |
|---|---|
| 构建 | `add_plugin(<Name>)` → `add_library(<Name> SHARED)`，链接 `Falcor`；输出到 `<build>/bin[<cfg>]/plugins/` |
| 汇总 | 所有 `add_plugin` 目标被追加到全局属性 `FALCOR_PLUGIN_TARGETS`，CMake 据此生成 `plugins/plugins.json` |
| 依赖 | `Mogwai` 与 `FalcorPython` 都 `add_dependencies` 到全部插件 |
| 加载 | `PluginManager::loadAllPlugins()` 读 `<bin>/plugins/plugins.json` → `loadLibrary(plugins/<Name>.dll)` → 调 `registerPlugin(registry)` |
| 注册 | `registry.registerClass<RenderPass, HelloPass>()`（宏 `FALCOR_PLUGIN_CLASS` 提供类型名与描述） |

由此推出两条硬规则：

- **插件 DLL 与 Mogwai 必须同配置**（Debug/Release 混用会加载失败或崩溃）。
- **改了 C++ 必须重启 Mogwai**：插件在进程启动时加载，没有热重载。

## 4. 着色器

```cmake
target_copy_shaders(HelloPass RenderPasses/HelloPass)
```

→ 源 `shaders/HelloPass.cs.slang` 部署到 `<bin>/shaders/RenderPasses/HelloPass/`，
代码里用 `"RenderPasses/HelloPass/HelloPass.cs.slang"` 加载。这是上游 pass 的统一写法，
照着写就不会错。

`F5`（Mogwai）会重载着色器，**不需要**重建 DLL——这是日常迭代最快的一条路。

共享 `.slangh` 暂时没有自动部署机制（`target_copy_shaders` 只拷目标自己的源文件）。
现状与将来做法见 `research/shared/shaders/Eidolon/README.md`，别在没验证的情况下假设
include 路径可用。

## 5. 帧资源契约

多个 pass 之间（渲染 → 降噪 → 超分 → 累积）要共享的不只是纹理，还有"这是第几帧、
累积多少样本、历史是否有效"。统一走 render graph 的 `InternalDictionary`
（C++ 侧 `RenderData::getDictionary()`），键名集中在
`research/shared/include/Eidolon/Common.hpp`：

| 键 | 类型 | 生产者 | 消费者 |
|---|---|---|---|
| `eidolon/frameIndex` | uint32 | 渲染 pass | 累积/时域 pass |
| `eidolon/spp` | uint32 | 渲染 pass | 降噪、参考帧判定 |
| `kRenderPassRefreshFlags`（上游） | flags | 任何改了视觉参数的 pass | TAA/累积（据此清历史） |

纹理侧约定（当前最小集，后续按需扩展并更新此表）：

| 通道 | 格式 | 含义 |
|---|---|---|
| `color` | RGBA16F | HDR 辐亮度 |
| `depth` | D32F | 深度（生产者负责说明是设备深度还是线性视深） |
| `motion` | RG16F | 屏幕空间运动矢量（像素） |

新加通道前先问：**能不能用已有的？** 每加一个就要同步改所有消费者。

## 6. 命名规则（会变成硬约束的地方）

| 东西 | 规则 | 为什么 |
|---|---|---|
| 插件库 | PascalCase，字母开头，只含 `[A-Za-z0-9_]` | 同时是目录名、CMake target、DLL 文件名、C++ 类名 |
| pass 类型名 | 与类名一致（`FALCOR_PLUGIN_CLASS` 第一个参数） | 图脚本里 `createPass("HelloPass")` 用它 |
| 端口名 | 小写驼峰（`color`、`depth`、`motion`） | 图脚本里 `"HelloPass.color"` |
| 实验目录 | `NNNN-kebab-slug` | 时间序即目录序 |

## 8. 升级上游

```powershell
pwsh -File tools\upgrade-falcor.ps1 -Ref 9.0      # 或更新的 tag
```

顺序被脚本强制为：清覆盖层 → fetch → checkout → 子模块 → 重新注入 → reconfigure → 重建。
之所以要先清覆盖层：那个文件在我们控制下随时可重生成，但对 git 来说是脏工作区，
`checkout` 会拒绝。

`vendor/VERSION.md` 记录当前指针与实际 commit，升级后顺手更新。

## 9. 为什么不做的事

| 不做 | 理由 |
|---|---|
| fork Falcor 并长期维护补丁 | 升级变成合并地狱；`patches/` 只做逃生舱 |
| 自研 out-of-tree 插件 CMake（复刻 `add_plugin`） | 要复刻 include 目录、宏、输出目录、`plugins.json`，上游一动就碎 |
| 自建主循环 app | Mogwai + render graph 已经覆盖 95% 的研究循环；真需要时用 `research/apps/` |
| 引入 Git LFS | 目前没有需要入库的大文件；`.rdc` 与场景都不入库 |
